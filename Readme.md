## Памятка

### Локальная база данных

Запустите Docker Desktop. Перед первым запуском скопируйте `.env-example`
в `.env`, если файла ещё нет. Задайте в `.env` собственный пароль
`MONGO_INITDB_ROOT_PASSWORD` из латинских букв и цифр.
Существующие настройки приложения в `.env` нужно сохранить.

Выполняйте команды из корня проекта, где находится `package.json`:

```sh
docker compose up -d --wait
docker compose ps
```

MongoDB доступна на `127.0.0.1:27017`. Интерфейс mongo-express:
<http://localhost:8081>. Для входа используйте значения
`MONGO_INITDB_ROOT_USERNAME` и `MONGO_INITDB_ROOT_PASSWORD` из `.env`.
Оба порта доступны только с этого компьютера.

Строка подключения для приложения, запущенного в Windows:

```text
mongodb://<username>:<password>@127.0.0.1:27017/six-cities?authSource=admin
```

Замените `<username>` и `<password>` значениями из `.env`.
База `six-cities` и коллекции создаются при инициализации моделей Mongoose.
Документы появятся после первой записи данных.

Для запуска приложения с подключением к MongoDB выполните:

```sh
npm start
```

Приложение читает из `.env` параметры `DB_HOST`, `DB_PORT`, `DB_NAME`,
`MONGO_INITDB_ROOT_USERNAME` и `MONGO_INITDB_ROOT_PASSWORD`.
Значения порта и имени базы по умолчанию — `27017` и `six-cities`.
В логах появятся попытка подключения, успешное соединение и инициализация
приложения. Пароль и строка подключения в логи не выводятся.
Если подключиться не удалось, приложение сообщает об ошибке и завершается
с кодом 1. Для остановки нажмите `Ctrl+C`: соединение с базой закроется.

Остановить контейнеры с сохранением данных:

```sh
docker compose down
```

Данные хранятся в именованном томе `six-cities_data`
(в Docker Desktop — `six-cities_six-cities_data`).
Не добавляйте флаг `-v` к команде остановки: он удаляет том с данными.
Логин и пароль создаются только при первой инициализации пустого тома;
изменение `.env` не меняет пароль уже существующего пользователя MongoDB.

### Схемы данных

Модули находятся в `src/shared/modules`:

* `user` — пользователь, коллекция `users`: имя, email, аватар, пароль и тип.
  Email имеет уникальный индекс; пароль не включается в результаты обычных запросов.
* `offer` — предложение жилья, коллекция `offers`: все поля типа `Offer`.
  Поле `author` хранит `ObjectId` пользователя из `users`, а координаты
  `location` — вложенный документ без отдельной коллекции.

В обеих схемах включено `timestamps: true`: Mongoose автоматически задаёт
`createdAt` и обновляет `updatedAt` при сохранении и изменении документов.
Дата публикации `publishedAt` хранится отдельно от служебных дат.
Схема комментариев будет добавлена в следующем задании.
После запуска приложения коллекции `users` и `offers` могут быть пустыми;
для их заполнения используйте команду импорта ниже.

### Сервисы работы с данными

Каждый модуль содержит интерфейс сервиса и его реализацию:

* `UserService` / `DefaultUserService`: `create(data, salt)`, `findById(id)`
  и `findByEmail(email)`. При создании пароль хешируется алгоритмом `scrypt`;
  аргумент `salt` берётся из настройки `SALT`. Email сохраняется и ищется
  без пробелов по краям, в нижнем регистре. Повторный email отклоняется
  уникальным индексом MongoDB.
* `OfferService` / `DefaultOfferService`: `create(data)` и `findById(id)`.
  В данных для создания предложения `author` — строковый идентификатор
  ранее созданного пользователя. Сервис преобразует его в `ObjectId`.

Типы `CreateUserDto` и `CreateOfferDto` описывают входные данные для создания.
Служебные даты и идентификатор нового документа задаются автоматически.
Поиск возвращает документ либо `null`, если запись не найдена или
передан некорректный идентификатор. Создание предложения с некорректным
идентификатором автора завершается ошибкой.
Сервисы получают модели через конструкторы из контейнера зависимостей.
Команда импорта получает эти сервисы из контейнера.

### Контейнер зависимостей

В `src/container.ts` зарегистрированы модели `UserModel`, `OfferModel`
и сервисы `UserService`, `OfferService`. Их идентификаторы находятся
в `src/shared/types/component.ts`.
Модели зарегистрированы как готовые значения, а сервисы — в единственном
экземпляре на контейнер (`inSingletonScope`). Повторный запрос сервиса
возвращает тот же экземпляр с уже переданной моделью.

Например, `container.get<UserService>(Component.UserService)` возвращает
готовый сервис пользователей. Создавать модель или вызывать
`new DefaultUserService(...)` в коде приложения больше не требуется.

### Импорт TSV в MongoDB

Запустите контейнеры и выполните из корня проекта:

```sh
docker compose up -d --wait
npm run cli -- --import mocks/offers.tsv "mongodb://admin:PASSWORD@127.0.0.1:27017/six-cities?authSource=admin"
```

Замените `PASSWORD` значением `MONGO_INITDB_ROOT_PASSWORD` из `.env`.
Если меняли логин, замените также `admin`. Специальные символы логина
и пароля в URI должны быть закодированы через `encodeURIComponent`.
В `.env` или переменных окружения должна быть непустая `SALT` для
хеширования паролей авторов. Остальные параметры подключения команда
берёт из второго аргумента, а не из настроек запуска REST-приложения.

Для каждой строки команда ищет автора по email, при необходимости создаёт
его, а затем сохраняет предложение со ссылкой на пользователя.
Одинаковые авторы не дублируются. Повторный запуск добавляет предложения
заново; существующие данные пользователя и его пароль не меняются.
Файл читается потоком, предложения сохраняются по одному. В терминал
выводятся прогресс через каждые 100 000 предложений и итоговые количества;
документы, пароли и URI подключения не печатаются.

Соединение закрывается после завершения или ошибки. При ошибке команда
завершается с кодом 1 и сообщает количество уже сохранённых предложений;
предыдущие записи остаются в базе. Импорт не выполняется одной транзакцией.
Для `mocks/offers.tsv` в пустой базе результат — два предложения и один
пользователь. Просмотреть их можно в mongo-express в базе `six-cities`,
коллекции `offers` и `users`.
